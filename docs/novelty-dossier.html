Novelty and technical justification

Telling a crash from a speed breaker, on the device

An on-device machine-learning layer for a LoRa accident-alert system, trained on 31,090 verified real crashes and measured against the rule it replaces, the design specified in Assessment-6, and the published deep models for the same dataset.

ESP32 · MPU6050 · SX1278  |  Arush Mishra

1What is new, in one page

A threshold detector answers one question — was the jolt big? This system answers the question that actually matters on an Indian road: was it a crash, or a speed breaker, a pothole, or hard braking? Two gradient-boosted tree models run inside the ESP32. Model A decides crash or not, from 30 accelerometer and 7 gyroscope features over a 2.5 s window. Model B names everything else. Only a crash raises an SMS.

Every number in this dossier is measured on the held-out test split of VZCrash — 24,174 events, 4,221 of them real crashes reviewed by three trained annotators against dashcam footage, none of which the model saw during training.

2The problem with the rule it replaces

Low-cost accident detectors, including the first version of this project, declare a crash when acceleration crosses a fixed threshold — here |a| > 2.2 g. Four measured objections:

  1. Ordinary bad roads cross the threshold. In the PVS drives, a dashboard accelerometer reaches 2.5–3.5 g on rough and cobblestone stretches. The rule fires on 6.3 % of rough-road jolts.
  2. On real crash data it ranks poorly. Average precision 0.703, false-alarm rate 6.98 %.
  3. It cannot explain itself. One bit of output: no way to tell a driver, a fleet or a road authority that the jolt was a speed breaker.
  4. The original parameters were mutually inconsistent — 3.3 Hz sampling cannot resolve a 50–200 ms crash pulse, and a ±2 g range cannot represent a 2.2 g threshold. Both are fixed here (100 Hz, ±16 g), but fixing them does not address objections 1–3.

The nearest prior design inside this project is the Assessment-6 V2 specification: a 200 ms window, an 8-element feature vector, logistic regression. Implemented exactly as written and trained on the same data it scores 0.902 AP — a real improvement on the threshold, and 0.062 AP below what is proposed here. §7 shows the limiting factor is the 200 ms window, not the classifier.

6Algorithms evaluated, and the protocol

Protocol. VZCrash's official splits are used unchanged: fit on train (137,954 events → 160,097 triggered windows), choose thresholds on validation (27,175 events), report on test (24,174 events). Class weights balanced. Metrics are reported per event — did the device raise an alert during this 16 s event? — with crash events that never cross the trigger counted as misses.

9Against the published state of the art

      

      
Caveat, stated plainly. The published figures are computed over every event in the
        dataset, while this system only sees events crossing its 0.45 g trigger — untriggered crashes are counted as
        misses here, but the candidate set differs, so the comparison is indicative rather than strictly like-for-like.
        The defensible claim is that a microcontroller-sized model lands between the paper's physics baseline and its
        deep networks.

12Claim structure

      

        INDEPENDENT CLAIM · METHOD
        
A method of discriminating vehicular collisions from road-surface disturbances in a vehicle-mounted inertial
          sensing device, comprising: maintaining a rolling buffer of tri-axial acceleration and angular rate;
          estimating a gravity vector; detecting a candidate event when the gravity-referenced dynamic acceleration
          exceeds a threshold; forming an analysis window spanning a pre-trigger interval and a post-trigger interval;
          re-anchoring said window upon a subsequent larger disturbance; computing a feature vector in which
          acceleration is decomposed into components parallel and perpendicular to the estimated gravity vector, and in
          which angular rate is decomposed into components about and across said vector; evaluating a first trained
          ensemble classifier to produce a collision confidence; and selecting between immediate transmission, a
          time-limited operator-cancellable verification state, and classification by a second trained ensemble
          classifier into road-disturbance categories, according to bands of said confidence.

      

      
Dependent claims. The re-anchoring criterion (N3); the horizontal velocity-change feature (N1);
        yaw-versus-tilt separation (N5); the two-model split and their independent training corpora (N2); transmission
        of class and confidence over a sub-GHz link with receiver-side de-duplication (N8); the flattened-tree float32
        deployment with verified decision parity (N6); speed-scaled pulse augmentation for low-severity impacts (N7).

    


    

      
13Reproducibility

      

      
Seeds are fixed (42). LightGBM training is not bit-reproducible across runs because of
        multithreaded histogram ties, so the invariant enforced is that the exported firmware header matches the saved
        model — which verify_firmware.py checks on every export.
